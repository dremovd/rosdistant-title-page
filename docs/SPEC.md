# Спецификация: генератор титульных листов ТГУ / Росдистант

**Версия:** 1.1  
**Дата:** 20.10.2026  
**Статус:** MVP реализован (`src/`, сайт: https://dremovd.github.io/rosdistant-title-page/); шаблон — `template/title-template.docx`, справочник — `data/catalog.json`  
**Исходный образец:** `source/Титульный 2026.docx` (предоставлен пользователем, хранится неизменным)  
**Хостинг:** GitHub Pages

**Изменения в 1.1:** уточнено описание исходного DOCX по результатам разбора XML (§3), добавлена карта разметки шаблона (§3.2), закрыт вопрос P0 о CORS — live-обновление из браузера невозможно (§4.4, §10), зафиксирован деплой на GitHub Pages (§8.1), добавлены критерии A14–A18.

## 1. Цель и основные решения

Создать общедоступную **статическую веб-страницу**, позволяющую студенту Тольяттинского государственного университета (в том числе обучающемуся через Росдистант) быстро заполнить и скачать титульный лист для практического задания.

Ключевые требования:

1. **Никакого прикладного сервера, регистрации, авторизации, базы данных и отправки персональных сведений.** Приложение развёртывается на **GitHub Pages** (см. §8.1).
2. **Всё заполнение, обработка, формирование DOCX и скачивание выполняются в браузере пользователя.** Сайт не отправляет введённые ФИО, группу, преподавателя и содержание работы куда-либо.
3. **Внешний вид результата основан на приложенном DOCX**, а не на приблизительно похожей HTML-странице.
4. Личные данные и последние настройки запоминаются **локально в браузере**, чтобы следующий титульный лист требовал минимум действий.
5. Справочники институтов, подразделений, направлений, профилей и дисциплин собираются из официальных публичных страниц ТГУ **на этапе сборки сайта** (GitHub Actions) и публикуются вместе с ним. Загрузка из браузера пользователя невозможна: `tltsu.ru` не отдаёт заголовок CORS (проверено 20.10.2026, §4.4).
6. Пользователь может вручную изменить **любое** автоматически подставленное значение до экспорта.

**Архитектурное решение для первой версии:** браузерное приложение + комплект статических ресурсов + встроенный справочник, обновляемый при пересборке сайта. Онлайн-обновления справочника из браузера нет. Прокси или serverless-функции **не входят в MVP**, поскольку нарушают требование полной статичности.

## 2. Границы MVP

### Входит

- Выбор образовательной программы через последовательность взаимосвязанных списков.
- Автозаполнение известной информации из открытых справочников.
- Ручное заполнение и исправление всех полей.
- Локальное сохранение постоянных реквизитов студента.
- Формирование **одностраничного DOCX** по предоставленному шаблону.
- Скачивание готового файла без загрузки данных на сервер.
- Работа при недоступности сайта ТГУ и при заблокированных междоменных запросах.
- Отображение даты актуальности справочника и предупреждений о сомнительных соответствиях.

### Не входит

- Авторизация в личном кабинете Росдистанта или СДО.
- Поиск студента по фамилии и получение номера группы из закрытых систем.
- Гарантированное автоматическое определение преподавателя, проверяющего конкретную работу.
- Скрапинг страниц, доступных только после входа.
- Генерация содержания самой практической работы.
- Массовое формирование листов, отдельное мобильное приложение, синхронизация между устройствами.
- Обязательный PDF-экспорт: конвертация DOCX в PDF в браузере с точным сохранением Word-вёрстки не считается доказанной.

## 3. Требования исходного DOCX

Изучен **один исходный титульный лист**. Он содержит:

- лист **A4**, один раздел; поля: верхнее 2 см, нижнее 2 см, левое 3 см, правое 1,5 см; колонтитулов нет;
- шапку Минобрнауки РФ и полное наименование ТГУ;
- фирменную графику: **одно JPEG-изображение на всю страницу** (1845×2607 px, «за текстом», привязано к первому абзацу со смещением −2,43 см). Геометрические элементы и знак Росдистанта — часть этой картинки, отдельного логотипа нет;
- блок образовательной программы, в том числе подписи-пояснения и горизонтальные линии;
- заголовок «ПРАКТИЧЕСКИЕ ЗАДАНИЯ №»;
- строку курса, необязательный вариант;
- таблицу с реквизитами обучающегося, группы и преподавателя;
- нижнюю строку «Тольятти 2026».

Технически в DOCX присутствуют **две таблицы и встроенное изображение JPEG**. Линии под полями — это границы ячеек таблиц, а не символы подчёркивания.

**Особенности исходника, выявленные при разборе XML:**

- После «Тольятти 2026» стоит **разрыв страницы**, поэтому исходный файл имеет пустую вторую страницу. Вероятно, это сделано, чтобы студент вставлял работу со второй страницы.
- Абзац «Тольятти 2026» оформлен стилем **«Заголовок 1»** (попадёт в автоматическое оглавление) и имеет отступ первой строки 1,25 см при выравнивании по центру (визуальный сдвиг вправо). Город и год — один фрагмент текста.
- Заголовок «Практические задания №» разбит на 5 фрагментов; прописные буквы задаются форматированием (caps). Форма множественная.
- Курс вставляется между подчёркнутыми кавычками «»; под ним подпись без линии.
- Строка «Вариант ____ *(при наличии)*» содержит заполнитель и подсказку.
- Ячейки значений «Обучающегося», «Группа», «Преподаватель» пустые; ширина 7,5 см, линия под ними 1,5 pt. Под группой подписи-пояснения нет.
- Основной шрифт — Times New Roman; размеры заданы явно (14 pt значения, 12 pt надстрочный курсив подписей, 16 pt заголовок).
- У таблицы 1 ширина ячеек (9627) не совпадает с сеткой (9355).
- Метаданные: автор «User», последним правил «Archirect», в описании картинки путь `C:\Users\user\Desktop\фон.jpg`. При генерации требуется сохранить исходную структуру документа, включая графику, размеры, стили, таблицы, линии, интервалы и расположение текста. Замена на скриншот или изображение всей страницы недопустима: результат должен оставаться редактируемым документом Word.

**Подготовка шаблона:** статический `.docx` с техническими плейсхолдерами готовится *до публикации* сайта скриптом `tools/build_template.py` (см. §3.2). Это не является серверной обработкой при использовании. Сам генератор лишь заполняет такой файл в памяти браузера. Нельзя полагаться на простую глобальную замену строк в `document.xml`, поскольку Word может разбивать видимый текст на несколько XML-фрагментов (`runs`).

### 3.1. Поля документа

| ID | Поле в шаблоне | Источник | Правило |
|---|---|---|---|
| `institute` | Полное название института | Справочник → ручная правка | Буквальное официальное название |
| `department` | Кафедра / департамент | Справочник → ручная правка | Печатается одной строкой вместе с типом, в официальном написании: «Департамент частного права», «Кафедра «Педагогика и психология»». Кавычки берутся из справочника, не добавляются автоматически |
| `direction` | Код и название направления | Справочник → ручная правка | Например «40.04.01 Юриспруденция» |
| `profile` | Направленность / профиль | Справочник → ручная правка | Точное название выбранной программы |
| `assignment_number` | № практического задания | Ввод | Печатать рядом с «№», не оставлять пустой «№» в готовом листе. Свободный текст: «2», «1–3», «1, 2» (заголовок во множественном числе) |
| `course` | Название учебного курса | Справочник → ввод/правка | Печатать внутри кавычек «…» |
| `variant` | Вариант (при наличии) | Необязательный ввод | Заполнен → «Вариант N» без «____» и без «(при наличии)». Пусто → абзац остаётся пустым (высота строки сохраняется) |
| `student` | Обучающегося | Локальный профиль | Формат шаблона: «И.О. Фамилия»; разрешить правку представления |
| `group` | Группа | Локальный профиль / ввод | Не угадывать по фамилии |
| `teacher` | Преподаватель | Подсказки / ввод | Формат «И.О. Фамилия»; не принимать публичную связь «дисциплина ↔ преподаватель» за доказательство назначения проверяющего |
| `city` | Тольятти | Постоянная | Не изменяется без явной ручной правки (в MVP можно скрыть из формы) |
| `year` | Год внизу страницы | Текущий год браузера → правка | По умолчанию текущий календарный год |
| `page_break` | Пустая вторая страница | Переключатель | По умолчанию **включено**, как в исходнике: после листа разрыв страницы, студент пишет работу со второй страницы. Выключено: ровно одна страница |

Наименование министерства, организационно-правовая форма и полное название вуза остаются **из предоставленного шаблона**, пока не принято отдельное решение об их обновлении. Не подменять автоматически эти юридически значимые реквизиты по догадке.

### 3.2. Разметка шаблона

Шаблон `template/title-template.docx` собирается из исходника скриптом `tools/build_template.py`. Каждая замена проверяется на точное число вхождений, поэтому изменение исходника не пройдёт молча. Синтаксис — docxtemplater (`{tag}`, `{#flag}…{/flag}`), опции `paragraphLoop: true`, `linebreaks: true`.

| Место в документе | Было | Стало |
|---|---|---|
| Абзац над таблицей 1 | Гуманитарно-педагогический институт | `{institute}` |
| Таблица 1, строки 2/4/6 | кафедра / направление / профиль | `{department}`, `{direction}`, `{profile}` |
| Заголовок | `… № ` | `… № {assignmentNumber}` (тот же фрагмент: жирный, caps, 16 pt) |
| Курс | `«»` (подчёркнуто) | `«{course}»` |
| Вариант | `Вариант ____ (при наличии)` | `{#variant}Вариант {variant}{/variant}` |
| Таблица 2, пустые ячейки | — | `{student}`, `{group}`, `{teacher}` (14 pt) |
| Низ страницы | «Тольятти 2026», Заголовок 1, отступ 1,25 см, разрыв страницы | Обычный абзац по центру, 14 pt: `{city} {year}`, затем `{#pageBreak}`разрыв`{/pageBreak}` |
| Таблица 1, ширина ячеек | 9627 | 9355 (по сетке) |
| Метаданные | автор, правщик, путь к картинке | очищены |

Шапка (министерство, ФГБОУ ВО, «Тольяттинский государственный университет»), подписи-пояснения, линии, фон и поля не меняются. Тест заполнения: `npm run test:template` (проверяет отсутствие тегов, вариант, разрыв страницы, экранирование XML и наличие фона).

**Пример образовательной иерархии (не единственный пресет):**

- Институт права;
- Департамент частного права;
- 40.04.01 Юриспруденция;
- Гражданское право и процесс;
- форма обучения: заочная (нужна для выбора справочных данных, на листе не печатается).

Приложенный DOCX при этом содержит **другой пример**: Гуманитарно-педагогический институт → Кафедра «Педагогика и психология» → 37.04.01 Психология → Психологическое консультирование. Следовательно, приложение **не должно быть жёстко привязано к юриспруденции**.

## 4. Справочные данные и их достоверность

### 4.1. Официальные открытые источники

| Данные | Основной источник | Особенности |
|---|---|---|
| Оргструктура, названия институтов и подразделений | https://www.tltsu.ru/sveden/struct | Публичная страница и схема структуры; возможны изменения HTML; структурная схема может быть PDF |
| Состав институтов, страницы кафедр/департаментов | https://www.tltsu.ru/education/institutions | Через страницы подразделений доступны связанные направления и профили |
| Образовательные программы и дисциплины | https://www.tltsu.ru/sveden/education | Учитывать код, уровень образования, профиль, форму обучения; по возможности год набора |
| Преподаватели | https://www.tltsu.ru/sveden/employees → `/sveden/direction/<программа>` | Таблица «Информация о составе педагогических работников образовательной программы»: ФИО, должность, дисциплины **в этой программе**. Не равно списку проверяющих конкретного курса/группы. Страница сотрудника (`/sveden/employees/<фамилия_имя_отчество>`) содержит контакты — их не собираем |

| Пример подразделения | https://www.tltsu.ru/education/institutions/institut-prava/departament-castnogo-prava | Публично указаны 40.04.01 и профиль «Гражданское право и процесс (Заочная)» |

Страницы подразделений и раздел образовательных программ доступны для чтения без авторизации, но **CORS закрыт**: 20.10.2026 запросы с заголовком `Origin` к `https://www.tltsu.ru/sveden/education` и `https://www.tltsu.ru/education/institutions` вернули `200 OK` без `Access-Control-Allow-Origin`. Браузерный `fetch()` со стороннего домена (в том числе `*.github.io`) прочитать их не сможет.

### 4.2. Модель справочника

Локальный справочник должен содержать:

- `source_url`, `fetched_at` или дату ручного обновления, `catalog_version`;
- институт (ID и отображаемое имя);
- структурное подразделение (ID, имя, тип, принадлежность институту);
- программу (код, название направления, профиль, уровень, форма обучения; год набора, **только если известен**);
- явные связи «подразделение ↔ программа», допускающие неоднозначность;
- дисциплины, относящиеся к **конкретной программе**, а не просто кафедре;
- при наличии: варианты преподавателей и источник такой связи, но **без автоматического назначения конкретного проверяющего**.

Использовать устойчивые внутренние идентификаторы и хранить официальные названия как отдельные значения. Списки могут изменяться, поэтому не основывать связи на порядковых номерах строк или DOM-позициях.

### 4.3. Приоритет и разрешение конфликтов

1. Явный выбор или исправление пользователя всегда имеет приоритет в его документе.
2. Данные программы из официального раздела образования приоритетнее общего списка дисциплин подразделения.
3. Официальная страница подразделения используется для связей «подразделение ↔ профиль».
4. Структура ТГУ используется для актуального названия подразделения и его уровня в иерархии.
5. Если по одной программе найдено более одного подразделения либо несогласованные наименования, **не выбирать молча**: показать варианты и ссылки на первоисточники.
6. Не выводить группу по фамилии и не считать преподавателя проверяющим на основании публичного перечня сотрудников.

### 4.4. Загрузка данных в полностью статической архитектуре

**Справочник встроен в сайт.** Файл `JSON` публикуется вместе со статикой, работает без междоменных запросов и доступен сразу после открытия сайта. В интерфейсе отображается дата его обновления. Ввод и исправление доступны при любой полноте справочника.

**Обновление — при сборке, а не в браузере.** Скрипт парсинга запускается в GitHub Actions (вручную через `workflow_dispatch` и по расписанию, например раз в неделю). Серверный запрос к `tltsu.ru` не ограничен CORS и не содержит данных пользователей.

Правила обновления:

- Тайм-аут запроса; при сетевой ошибке сборка сохраняет предыдущий справочник и сообщает об ошибке в логе Actions.
- Не принимать подозрительно пустой или повреждённый ответ: новый справочник сравнивается с предыдущим (резкое сокращение числа записей → ошибка, а не публикация).
- Источники — по заранее разрешённому списку URL.
- Парсеры версионируются по типам страниц; изменение вёрстки сайта ТГУ должно ронять сборку, а не давать неверное заполнение.
- Изменения справочника оформляются коммитом (или pull request), чтобы diff можно было просмотреть.

**Жёсткое ограничение:** в браузере **не** обходить CORS через `no-cors`, `<iframe>`, JSONP или публичные CORS-прокси.

## 5. Интерфейс и сценарий пользователя

### 5.1. Основной сценарий

1. Пользователь впервые открывает статический сайт; получает готовую форму, данные можно заполнить без регистрации.
2. Первым вводит **номер группы** и ФИО. По номеру группы сайт предварительно заполняет программу (см. §5.3), затем пользователь проверяет или уточняет институт → подразделение → направление → профиль.
3. Приложение показывает подходящие дисциплины; пользователь выбирает курс **или вводит своё название**.
4. Вводит ФИО, группу, номер практического задания, вариант при необходимости, преподавателя и год.
5. Видит сводку и предпросмотр титульной страницы с предупреждениями по незаполненным или неоднозначным полям.
6. Нажимает «Скачать DOCX». Браузер формирует документ локально на базе шаблона и скачивает его.
7. При следующем посещении личные реквизиты и последний выбор программы восстановлены автоматически.

### 5.2. Организация формы

**Блок «Программа» (запоминается):** институт, подразделение, код/направление, профиль, форма обучения, при наличии год набора.

**Блок «Студент» (запоминается):** полное ФИО либо готовая форма «И.О. Фамилия», номер группы. Сохранение сразу после изменения с небольшим debounce; никаких внешних запросов.

**Блок «Работа» (новый для каждого документа, допускаются последние значения):** название дисциплины, номер задания, вариант, ФИО преподавателя, год.

Поля-справочники одновременно поддерживают выбор и свободный ввод. Неочевидные автоматически подобранные значения отмечаются как **подсказки**, а не как подтверждённые назначения.

Предусмотреть «Сбросить данные», «Очистить только текущую работу», индикацию локального сохранения и ссылку на официальную страницу программы/подразделения. Дополнительный экспорт/импорт профиля в JSON полезен, но не обязателен в MVP.

### 5.3. Заполнение по номеру группы

Номер группы вида `ЮРмд-2406а`: префикс направления (`ЮР`), уровень (`б` бакалавриат, `м` магистратура, `с` специалитет, `спо`), признаки формы, год набора (`24`), номер и подгруппа.

- Снапшот списка групп (`data/groups.json`) собирается при сборке сайта из открытого API расписания. В браузере к API не обращаемся: номер группы не уходит на сторонний сервер (A13), хотя CORS у `its.tltsu.ru` открыт.
- Институт берётся из снапшота; если группы там нет — подбирается по буквам.
- Направление подбирается по совпадению префикса с названием направления (начало слова, первые буквы слов, буквы по порядку) в пределах института и уровня; при равных баллах показываются все варианты. Справочника префиксов ТГУ не публикует, поэтому возможны ошибки (например, `МР` — «Мехатроника и робототехника», а не «Машиностроение»).
- Признак формы из API (1 — очная, 2 — заочная/очно-заочная) сужает список программ, только если что-то остаётся.
- Результат — **предварительное заполнение с пометкой «проверьте»**: подходящие программы показываются первыми в списке, единственный вариант выбирается сам. Ручной выбор пользователя не перезаписывается — вместо этого предлагается кнопка «Заполнить программу по группе».
- Профиль по номеру группы не определяется (нет открытых данных о соответствии номеров профилям).

### 5.4. Валидация

- Перед скачиванием проверять: направление, профиль, курс, обучающийся, группа, номер задания; проверять корректность года.
- Неизвестный преподаватель: предупреждение с возможностью вручную подтвердить скачивание без него. **Не выдумывать ФИО**.
- Формат инициалов обучающегося и преподавателя: поддерживать ручную правку, дефисы в фамилиях, отсутствие отчества и нестандартные имена.
- Избегать двойных кавычек вокруг курса, если пользователь уже ввёл «…».
- При изменении программы очищать зависимые значения только тогда, когда они перестали соответствовать новому выбору; не терять вручную введённый текст без предупреждения.
- Все текстовые данные экранируются для XML, управляющие символы и недопустимые символы имени файла обрабатываются безопасно.

## 6. Формирование документа

1. Шаблон DOCX должен поставляться вместе со статическими файлами сайта; его исходная графика, таблицы и форматирование сохраняются.
2. При экспорте шаблон загружается **в память браузера**. Подстановка переменных и упаковка DOCX выполняются на клиенте, без вызовов удалённого API.
3. Результат: валидный, редактируемый `.docx` на **одной странице A4**, открываемый в Microsoft Word и LibreOffice.
4. Текст должен оставаться редактируемым текстом, а не картинкой. Нельзя потерять линии, фирменный фон, логотип, шапку, сноски-подписи и нижний колонтитульный блок.
5. Длинные наименования корректно переносятся без наложения на линии/иллюстрации; если сохранить одну страницу невозможно, пользователь получает предупреждение до скачивания.
6. Не оставлять в конечном файле технические плейсхолдеры, подчёркивания-заполнители и пустые кавычки.
7. Рекомендуемый шаблон имени файла: `Титульный_<Дисциплина>_задание-<Номер>_<Год>.docx` (нормализация символов и разумное ограничение длины).
8. Предпросмотр может быть HTML-представлением, но **не считается эталоном** пиксельного соответствия Word. Эталон качества: визуальная сверка выгруженного DOCX с исходным документом в Word/LibreOffice.

**Допустимая техническая основа:** библиотека для работы с ZIP/OOXML и заполнения DOCX, включённая в статическую сборку локально. Например, `PizZip` + `docxtemplater` после предварительной разметки шаблона. Это лишь ориентир, **не требование использовать конкретную библиотеку**. Облачные сервисы конвертации запрещены.

**PDF:** отдельная необязательная будущая функция. Добавлять только после подтверждения корректной клиентской вёрстки; браузерная печать HTML и конвертация DOCX в PDF не должны объявляться идентичными Word по умолчанию.

## 7. Локальное хранение и конфиденциальность

- Для персональных реквизитов: `localStorage` с версией схемы и безопасной миграцией. Ключи — с префиксом приложения: на GitHub Pages все проекты пользователя живут на одном origin `<user>.github.io` и делят `localStorage`.
- Данные привязаны к браузеру, устройству и адресу сайта: **между устройствами автоматически не синхронизируются**.
- Очистка данных браузера удалит профиль. В приватном режиме сохранение может отсутствовать; интерфейс не должен выдавать его за гарантированное.
- Без аналитики, внешних скриптов, CDN-шрифтов и сторонних виджетов, способных передать личные данные. Все JS/CSS/библиотеки/шаблон должны поставляться как локальные ресурсы сайта.
- Не запрашивать пароль, логин СДО, СНИЛС, адрес, телефон или сведения, не нужные для титульного листа.
- Кнопка полного удаления локальных данных приложения (профиль и последние значения); удалять только ключи со своим префиксом.
- Сайт в браузере не обращается к `tltsu.ru` и другим доменам: все запросы — только к собственным статическим файлам.
- Метаданные выходного DOCX: автор и правщик пустые, даты создания/изменения — момент генерации; ФИО студента в метаданные не пишется.

## 8. Технические ограничения и развёртывание

- **Хостинг:** GitHub Pages (§8.1). Нет собственного backend/API, серверной БД и server-side rendering.
- **Состав публикации:** HTML, CSS, JS и локальные зависимости, подготовленный DOCX-шаблон, локальный справочник, изображения/иконки при необходимости.
- **Браузеры:** актуальные Chrome, Firefox, Safari (desktop и mobile), Edge; в частности проверить Safari на macOS/iOS.
- **Сеть:** сайт должен создавать DOCX после загрузки всех его статических ресурсов даже при недоступном `tltsu.ru`. Полностью автономная работа после первой загрузки (Service Worker/PWA) желательна, но не обязательна для MVP.
- **Наличие live-справочника не должно быть условием работоспособности генератора.**
- **Нельзя гарантировать открытие сайта простым двойным кликом по `index.html` (`file://`)**, если используются загрузки внешних локальных файлов. Целевой вариант: статический сайт, открываемый по HTTPS. Поддержка `file://` возможна только при соответствующей упаковке всех ресурсов и отдельно тестируется.

### 8.1. GitHub Pages

- **Публикация:** GitHub Actions (`actions/upload-pages-artifact` + `actions/deploy-pages`), источник Pages — «GitHub Actions». Публикуется только каталог сборки (`site/` или `dist/`), а не весь репозиторий: исходный DOCX, скрипты и `node_modules` наружу не попадают.
- **Адрес:** `https://<user>.github.io/<repo>/` — сайт живёт в подкаталоге. Все пути к ресурсам (шаблон, справочник, JS, CSS) **относительные** или учитывают base path; абсолютные `/template.docx` не работают. Пользовательский домен — опционально, без изменения кода.
- **Заголовки HTTP не настраиваются.** CSP задаётся через `<meta http-equiv="Content-Security-Policy">`: `default-src 'self'; connect-src 'self'; img-src 'self' data: blob:; object-src 'none'; base-uri 'self'; form-action 'none'`. `frame-ancestors` через meta не работает — защиты от встраивания во фрейм нет, это допустимо (на странице нет действий, опасных при clickjacking).
- **Кэш:** Pages отдаёт файлы с `Cache-Control: max-age=600`. Чтобы после обновления не смешались старый JS и новый справочник/шаблон, имена ресурсов содержат хэш содержимого (или `?v=<версия>`), а `index.html` ссылается на них.
- **MIME:** `.docx` отдаётся как `application/vnd.openxmlformats-officedocument.wordprocessingml.document`, но генератор читает шаблон через `fetch().arrayBuffer()`, тип не важен.
- **Jekyll:** в публикуемом каталоге лежит `.nojekyll` (если используется не Actions-деплой, а публикация из ветки).
- **Репозиторий публичный** (бесплатные Pages). Поэтому в репозитории нет персональных данных; тестовые ФИО — вымышленные.
- **Ограничения Pages:** сайт до 1 ГБ, мягкий лимит трафика 100 ГБ/мес — с запасом для шаблона ~200 КБ и справочника.

**P1. Подчёркивание номера задания.** У знака конца абзаца заголовка в исходнике стоит подчёркивание — возможно, номер задуман подчёркнутым, как курс. Сейчас номер печатается без подчёркивания. Уточнить по образцам кафедр.

**Сделано в реализации:** справочник собирается со страниц подразделений `tltsu.ru/education/institutions/<институт>/<подразделение>`: на них есть и программы (код, направление, профиль, форма обучения, уровень), и дисциплины по каждому профилю. На 20.10.2026: 11 институтов, 45 подразделений, 142 программы, у всех есть дисциплины. Преподаватели берутся из раздела «Педагогический состав»: по каждой программе (код + профиль) — ФИО, должность и дисциплины, которые человек ведёт в этой программе (`data/staff.json`; телефоны и почта не сохраняются; на 20.10.2026 — 587 преподавателей, сопоставлено 134 программы из 142, у остальных таблица на tltsu.ru пустая или ссылка ведёт на другую программу). Если выбранный курс совпадает с дисциплиной преподавателя, под полем «Преподаватель» показываются кнопки-подсказки; сам сайт ничего не подставляет. Дополнительно собираются личные страницы преподавателей (`/sveden/employees/<имя>`): подразделение и полный список дисциплин (без контактов). Если в таблице программы преподаватель курса не указан, показываются преподаватели того же института, у которых курс есть на личной странице, с пометкой «программа не указана»; сначала — из того же подразделения. Все преподаватели программы и ранее введённые имена — в подсказках поля. Названия с прямыми кавычками («Кафедра "Педагогика и психология"») при печати приводятся к ёлочкам, как в исходном DOCX.

**P1. Полнота справочника.** Определить, насколько широким должен быть стартовый снапшот: все программы ТГУ или поэтапное наполнение. При отсутствии записи всегда остаётся ручной режим.

**P1. Названия курсов.** Сопоставить каталог по программе, форме обучения и, где опубликовано, году набора; не представлять совокупный список кафедры как индивидуальные курсы студента.

**P1. Назначенный преподаватель.** В открытых данных есть преподаватели программы и их дисциплины — по ним показываются подсказки. Персонального проверяющего нужно подтверждать в СДО; поле остаётся пользовательским, автоподстановки нет.

**P2. PDF.** Решить, нужен ли он вообще; в MVP приоритет у точного редактируемого DOCX.

## 11. Критерий успешного продукта

Студент один раз выбирает программу и вводит ФИО с группой. При следующем задании ему достаточно указать **дисциплину, номер практической работы и преподавателя**, после чего он получает корректно оформленный титульный DOCX **одним нажатием**, без регистрации, сервера, передачи личных данных и необходимости вручную править шаблон Word.
